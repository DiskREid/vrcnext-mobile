# VRCNext Mobile 0.2.12 — исправление лога смены аватара

## Сравнение с текущей ПК-версией

Remote main VRCNext сверён с изученным коммитом
`0bfb467f89caa21893769f6495abe334febe08a3`. В обработчике `friend-update`
ПК извлекает ID файла из `currentAvatarImageUrl`, `currentAvatarThumbnailImageUrl`
или `iconUrl`, сравнивает с последним известным файлом и при изменении получает
название. Дополнительной подписки WebSocket нет. Локальный `AvatarChanged` из
игровых логов относится только к собственному аватару и не является источником
событий друзей.

В Android 0.2.11 были найдены конкретные пропуски:

- `iconUrl` игнорировался, хотя актуальная схема `User` в `friend-update`
  содержит это поле, а старых полей аватара в ней больше нет.
- Сравнивались только полное изображение с полным и миниатюра с миниатюрой.
  Переход из одного поля в другое мог не создать событие.
- Состояние `connecting` и ошибка наблюдения собственного местоположения
  сбрасывали также исходные данные аватаров. Первая смена затем могла стать
  новым исходным значением без записи.
- Разрешался только новый файл и только через AvatarDB. Поиск ПК содержит
  несколько резервных источников и умеет вернуть название без avatar ID.

## Обработка события

Изображение нормализуется до ID файла независимо от полного/уменьшенного поля,
CDN, версии, разрешения и query-подписи. Поддержаны доверенные пути с ID файла
без сегмента версии. Смена версии того же файла не считается выбором другого
аватара. Hidden/loading изображения по-прежнему не создают ложные переходы.

`iconUrl` сначала создаёт внутреннего кандидата: это может быть пользовательская
фотография. Кандидат не показывается и не сохраняется в ленту, пока точное
разрешение файла не подтвердит данные аватара. Неподтверждённая иконка, её ошибка
загрузки и возврат к прежнему аватару не должны выдавать ложную смену.

Список друзей остаётся только источником недостающих исходных данных. При
реальном событии предыдущий снимок можно восстановить из уже полученной строки
друга. Подключение WebSocket и остановка наблюдения посещений теперь прекращают
только наблюдение сессии, сохраняя исходные данные ленты. Очистка истории и смена
аккаунта по-прежнему полностью сбрасывают соответствующие наблюдения.

Нет обхода профилей, периодических проверок био/аватаров, счётчика и кнопки
обновления. Запросы метаданных выполняются только после полученного изменения.

## Откуда берётся название

Перенесена доступная часть цепочки ПК:

1. AvatarDB: `QUERY https://api.avtrdb.com/v3/avatar/resolve`,
   `{"file_ids":[fileId]}`; принимается только точный ключ ответа.
2. При отсутствии результата — avtr.icu: `QUERY https://avtr.icu/resolve`,
   `{"ids":[fileId]}`; также только точное соответствие файла.
3. При отсутствии результата в обеих базах — официальный `GET /file/{fileId}`.
   Название берётся только из серверного формата
   `Avatar - NAME - Image/Asset bundle/Unity package - ...`.

Название из официального файла можно показать без недоступного `avtr_` ID.
ID не выдумывается, произвольное имя иконки/галереи не считается аватаром.
Публичные базы используют отдельный нативный клиент без cookies и авторизации
VRChat. В них передаётся только ID файла; официальный `/file/` получает обычную
авторизацию через существующий транспорт VRChat. Ограничения 429 сохраняются.

Подписанная база vrcndb и её приватные ключи не переносятся. Поиск приблизительного
совпадения по названию не подменяет доказательство соответствия файла.

## Предыдущий → новый

Карточка показывает обе стороны: изображения, доступные названия и авторов.
Нажатие на старое или новое название открывает существующий поиск AvatarDB.
Если название неизвестно, это прямо указано; изображение и доступный ID остаются.
Непроверенная прежняя иконка скрыта до подтверждения: вместо фотографии
показывается неизвестная старая сторона. Подтверждение нового аватара при этом
не ждёт доступности старого файла. Старые односторонние записи совместимы
с прежней базой.

Оба файла разрешаются по фактически полученному переходу. Кеш и объединение
запросов исключают повторное чтение одного файла. Между физическими заданиями
минимум одна секунда, как в ПК-планировщике. Очередь ограничена 100 файлами,
кеш — 100 краткими записями; без событий нет запроса и таймера обхода.

Результат привязан к ID события, стороне и ID файла. Быстрые последовательные
смены A → B → C не присваивают старое название новому событию и не отбрасывают
правильные метаданные исторического перехода. Уточнение сохраняет исходные ID,
время и источник записи и переживает перезапуск.

## Проверки и ограничения

Проверяются современные `iconUrl` события, переход миниатюра → полное изображение,
восстановление исходного снимка, подключение после загрузки друзей, точные
резервные источники, имя без ID, смена пользовательской иконки, быстрые переходы,
обе стороны карточки/поиска, сохранение и отсутствие сканирования при простое.
Отдельным публичным запросом AvatarDB подтверждено реальное соответствие файла
`file_73bdcab2-a4f6-4652-a13a-45202d4c210d` аватару `VRoomba-gen`.

Это не проверка живого VRChat-аккаунта или физического Tecno/HiOS. Если VRChat
не передал изображение/ID либо серверные источники не раскрыли файл, данные
не угадываются. Доступность каждой базы на телефоне требует проверки устройства.
Био не опрашивается: оно фиксируется только из реально полученных полей;
ПК-фильтр Bio уже отмечен устаревшим из-за изменений API.
